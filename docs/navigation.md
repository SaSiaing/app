# 가족 가계부 — 네비게이션 정책

이 문서는 앱의 최상위 경로와 화면 이동 원칙을 정의합니다.
화면 흐름을 바꿀 때는 구현보다 이 문서를 먼저 수정합니다.

현재는 네비게이션 기반만 만드는 단계입니다. 탭별 상태 유지, 상세 화면 흐름,
알림과 외부 링크를 통한 딥링크 정책은 제품 화면이 확정된 뒤 결정합니다.

## 결정 배경

초기 화면은 홈, 내역, 예산, 통계, 설정의 다섯 영역으로 나눕니다. 사용자가 주요
영역을 오갈 수 있어야 이후 화면을 독립적으로 개발하고 확인할 수 있기 때문입니다.
예산은 계획을 관리하는 영역이고 통계는 실제 수입·지출 결과를 확인하는 영역이므로
별도의 최상위 탭으로 구성합니다.

- **최상위 경로만 먼저 만듭니다.** 상세 화면 흐름이 정해지기 전에 경로를 늘리면
  임시 구조가 정책으로 굳을 수 있습니다.
- **공통 하단 내비게이션을 사용합니다.** 다섯 영역은 앱의 주요 진입점이며 같은
  수준에 있습니다.
- **탭 화면은 임시 화면으로 시작합니다.** 상태가 없는 화면으로 구성해 탭 전환 시
  상태 유지 여부를 이번 구현에서 결정하지 않습니다.
- **딥링크 상세 경로는 아직 만들지 않습니다.** 알림, 인증, 접근 권한, 삭제된
  리소스 처리까지 함께 정해야 하기 때문입니다.

## 현재 확정된 범위

### 경로

| 경로 | 화면 | 하단 탭 | 현재 내용 |
|---|---|---|---|
| `/` | 앱 진입점 | - | `/home`으로 이동 |
| `/home` | 홈 | 홈 | 임시 화면 |
| `/transaction` | 내역 | 내역 | 임시 화면 |
| `/budget` | 예산 | 예산 | 임시 화면 |
| `/statistics` | 통계 | 통계 | 임시 화면 |
| `/settings` | 설정 | 설정 | 임시 화면 |

최상위 경로의 첫 구간은 `lib/features` 아래 기능 폴더 이름과 정확히 일치시킵니다.
내역과 예산처럼 하나의 기능 화면을 나타내는 이름은 단수형을 사용합니다.

```text
/transaction  → lib/features/transaction
/budget       → lib/features/budget
/statistics   → lib/features/statistics
/settings     → lib/features/settings
```

라우트 상수, 기능 폴더, 화면 파일과 화면 클래스도 같은 기능 이름을 기준으로
작성합니다. 예를 들어 `/transaction`은 `Routes.transaction`,
`transaction_screen.dart`, `TransactionScreen`으로 연결합니다. 상세 경로를 추가할
때도 최상위 경로 이름을 그대로 확장합니다.

### 구조도

![가족 가계부 네비게이션 구조](images/navigation-structure.png)

구조도의 수정 가능한 원본은
[`diagrams/navigation-structure.dot`](diagrams/navigation-structure.dot)입니다.

구조도를 수정한 뒤 저장소 루트에서 다음 명령으로 이미지를 다시 생성합니다.

```sh
dot -Tpng docs/diagrams/navigation-structure.dot \
  -o docs/images/navigation-structure.png
```

### 구현

- `MaterialApp.router`를 앱 진입점으로 사용합니다.
- `go_router`의 `ShellRoute`로 공통 하단 내비게이션을 구성합니다.
- 경로 문자열은 `core/routing/routes.dart`에서 한 곳에 정의하고 라우터와 하단 탭이
  같은 상수를 사용합니다.
- 하단 탭 선택 시 `context.go()`로 해당 최상위 경로로 이동합니다.
- 다섯 개의 탭 경로는 각 기능의 `widgets` 폴더에서 제목만 표시하는 임시
  `StatelessWidget` 화면을 사용합니다.
- `/`은 `/home`으로 리다이렉트합니다.
- 위젯 테스트에서 각 탭을 선택했을 때 대응하는 임시 화면이 표시되는지 확인합니다.

`ShellRoute` 선택은 상태를 초기화한다는 제품 결정이 아닙니다. 현재 임시 화면에는
보존할 상태가 없으며, 상태 유지 정책이 정해지면 라우터 구조를 다시 검토합니다.

## 상세 경로 방향

아래 경로는 향후 논의를 위한 예시이며 현재 구현 계약이 아닙니다.

```text
/transaction/:transactionId
/budget/:budgetId
/budget/:budgetId/history
```

상세 경로를 확정할 때는 다음 항목을 함께 결정합니다.

- 상세 화면에서 하단 내비게이션을 표시할지
- 상세 화면 진입에 `go()`와 `push()` 중 무엇을 사용할지
- 시스템 뒤로 가기와 탭 재선택이 어떻게 동작할지
- 리소스 식별자를 경로와 쿼리 중 어디에 둘지

## 알림과 딥링크 방향

알림을 선택해 특정 예산이나 내역으로 이동하는 기능이 필요할 수 있습니다. 알림
데이터는 화면 URL을 직접 저장하기보다 이동 목적과 리소스 식별자를 전달하는 방식을
우선 검토합니다.

```json
{
  "type": "budget_detail",
  "budgetId": "123"
}
```

앱이 이 데이터를 내부 경로로 변환하면 경로 구조가 바뀌어도 서버 알림 형식에 미치는
영향을 줄일 수 있습니다. 이 형식은 제안이며 아직 확정하지 않습니다.

## 아직 정하지 않은 정책

- [ ] 탭 전환 시 화면 상태와 스크롤 위치를 유지할지
- [ ] 탭마다 독립적인 네비게이션 스택을 사용할지
- [ ] 상태 유지가 필요할 때 `StatefulShellRoute.indexedStack`을 사용할지
- [ ] 탭을 다시 선택했을 때 첫 화면으로 돌아갈지
- [ ] 상세 화면에서 하단 내비게이션을 표시할지
- [ ] 알림 데이터와 내부 경로의 매핑 규칙
- [ ] 로그인 전 딥링크 진입 후 원래 목적지로 이동할지
- [ ] 접근 권한이 없거나 삭제된 리소스의 대체 화면
- [ ] Android App Links와 iOS Universal Links를 사용할지
- [ ] 알 수 없는 경로의 오류 화면과 복귀 동선

## 변경 규칙

- **네비게이션 구조를 수정할 때는 이 문서를 먼저 수정한 뒤 코드를 변경합니다.**
- 최상위 경로의 첫 구간, `lib/features`의 기능 폴더, 라우트 상수와 화면 이름은
  같은 기능 이름을 사용합니다.
- 네비게이션 구조를 변경할 때는 경로 표와
  `diagrams/navigation-structure.dot`을 먼저 수정하고,
  `images/navigation-structure.png`를 다시 생성한 뒤 코드를 변경합니다.
- 구조도 원본과 이미지가 현재 경로 및 탭 구성과 다르면 네비게이션 변경이 완료된
  것으로 간주하지 않습니다.
- 경로, 탭 구성, 라우트 계층, 상태 유지 방식, 뒤로 가기, 딥링크 동작을 바꾸는
  작업에는 모두 이 규칙을 적용합니다.
- 문서에 반영되지 않은 네비게이션 구조 변경은 확정된 정책으로 간주하지 않습니다.
- 미정 항목은 임시 구현을 근거로 확정된 것으로 간주하지 않습니다.
- 화면 구현 PR은 새 경로가 필요하면 이 문서의 경로 표를 함께 갱신합니다.
- API 경로나 서버 계약은 이 문서가 아니라 backend의 `docs/api.md`에서 관리합니다.
